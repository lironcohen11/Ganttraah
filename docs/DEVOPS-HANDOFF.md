# Ganttraah: מסמך מסירה לצוות DevOps

המסמך מיועד לצוות שמקבל לאחריותו את התפעול של Ganttraah ברשת הפנימית. הוא מסביר איך המערכת בנויה, איך מפעילים, מגבים ומעדכנים אותה, ומה פתוח.

פירוט שלב-אחר-שלב של ההתקנה כבר קיים, ואין טעם לשכפל אותו כאן:
- **התקנה על שרת (Windows או Linux):** `docs/DEPLOY-INTERNAL.md`.
- **התקנה על OpenShift:** `deploy/openshift/README.md`.

המסמך הזה משלים אותם, ומתמקד במה שצריך לדעת כדי להחזיק את המערכת לאורך זמן.

## 2. איך המערכת בנויה

| שכבה | מה יש בה |
|---|---|
| **דפדפן** (Chrome / Edge) | הממשק. מדבר עם השרת ב-HTTP (קבצים סטטיים, וה-API ב-`/api`), וב-WebSocket ב-`/ws` (עדכונים חיים, ומי צופה באיזו משימה) |
| **שרת Node.js** (`server/src/index.js`), פורט 8080 | Express 5 ו-ws 8. תהליך אחד שמגיש את הכול |
| **מסד נתונים** | PostgreSQL חיצוני (`DATABASE_URL`), או PGlite מובנה (`DATA_DIR`) |

**השרת** (`server/src`) כתוב ב-JavaScript רגיל, בלי שלב בנייה:

| קובץ | תפקיד |
|---|---|
| `index.js` | הפעלה, קבצים סטטיים, WebSocket, תחזוקה לילית, עצירה מסודרת (SIGTERM) |
| `api.js` | כל נקודות ה-API ובדיקות ההרשאה |
| `store.js` | כל שינוי עובר כאן: טרנזקציה, חישוב התזמון לפני ואחרי, היסטוריה, ביטול |
| `scheduler.js` | מנוע התזמון (תלויות, נתיב קריטי, מרווחים) |
| `calendar.js` | לוח עבודה וחגים עבריים, מחושבים מקומית |
| `db.js` | החיבור למסד: PostgreSQL או PGlite |
| `schema.sql` | מבנה המסד. רץ בכל הפעלה ויוצר רק מה שחסר |

**הממשק** (`client`) כתוב ב-React ו-TypeScript, ונבנה עם Vite לקבצים סטטיים ב-`client/dist`. השרת מגיש אותם ישירות.

**איך שינוי עובד:** כל שינוי בתוכנית רץ בטרנזקציה אחת. השרת קורא את כל התוכנית, מחשב את התזמון, מבצע את השינוי, מחשב שוב, רושם בהיסטוריה מה זז, ושומר צילום של המצב הקודם לטובת "ביטול". אחר כך הוא שולח לכל הדפדפנים הודעה ב-WebSocket, והם טוענים את התוכנית מחדש. התוכנית קטנה (עשרות עד מאות משימות), ולכן החישוב המלא הזה מהיר.

## 3. אפשרויות ההתקנה, והמצב של כל אחת

| אפשרות | קבצים | מצב |
|---|---|---|
| **OpenShift 4** | `Dockerfile`, `deploy/openshift/gantraah-postgres.yaml` (מומלץ) או `gantraah-pvc.yaml` | נבדק ב-Docker בתנאים של OpenShift: משתמש אקראי לא-root, קבוצה 0. המידע נשאר אחרי מחיקת פוד ואחרי הריגה קשה. |
| **שרת Windows או Linux עם Node** | חבילת zip מ-`deploy/build-offline.ps1` | נבדק. |
| **Docker Compose** (המערכת + PostgreSQL) | `deploy/docker-compose.yml`, `compose.env.example` | נכתב, ולא הורץ. |

**האימג':** בנוי על `node:24-alpine`, רץ כמשתמש 1001, ונבנה בשני שלבים. בשלב הראשון נבנה הממשק, ובשני נכנסות רק התלויות של השרת לסביבת ייצור. הבנייה דורשת גישה ל-npm, ולכן בונים בחוץ ומעבירים קובץ `tar` (`docker save`).

**משאבים** (מתוך קובץ ה-OpenShift): בקשה של `100m` CPU ו-`256Mi` זיכרון, ותקרה של `1Gi`. בבדיקת עומס עם 4 משתמשים ו-400 שינויים במקביל, השרת לא התקרב לגבולות האלה.

## 5. הנתונים

**מיגרציות:** `schema.sql` רץ בכל הפעלה. הוא יוצר טבלאות ועמודות שחסרות (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`), ואף פעם לא מוחק. חוץ ממנו יש כמה מיגרציות חד-פעמיות בקוד, שבודקות את עצמן ורצות פעם אחת. אין שלב נפרד של "עדכון מסד".

**הטבלאות העיקריות:**

| טבלה | מה יש בה |
|---|---|
| `projects`, `tasks`, `dependencies` | התוכנית עצמה |
| `units` | המבנה הארגוני (הנהלת ענף › מדורים › צוותים) |
| `sessions` | כניסות פעילות (עוגייה `gantraah_sid`) |
| `settings` | הגדרות: לוח העבודה, סיסמת הנהלת הענף (hash), מונה גרסה של התוכנית |
| `special_days` | ימי חופש מיוחדים |
| `audit_log` | היסטוריית שינויים |
| `undo_stack` | צילומי מצב לביטול ולביצוע שוב |
| `notifications`, `notification_seen`, `notification_reads` | העדכונים בפעמון ומה כל מסגרת קראה |
| `task_delays` | סיבות הדחייה של משימות |
| `favorites` | מועדפים לכל מסגרת |
| `backlog` | משימות בלי תאריך (חדש ב-1.8) |

**ניקוי אוטומטי** (בהפעלה, ואחר כך פעם ביום): היסטוריה ישנה מ-`HISTORY_DAYS`, עדכונים בפעמון ישנים מ-180 יום, וצילומי ביטול ישנים מ-14 יום. במסד המובנה רצים בנוסף בכל לילה `VACUUM` ו-`CHECKPOINT`, וזה לוקח בערך שנייה. כך המסד לא גדל בלי סוף.

## 6. תפעול שוטף

**בדיקת תקינות:** `GET /healthz` מחזיר 200 עם `ok:true` כשהשרת מחובר למסד. ב-OpenShift הוא משמש גם ל-readiness וגם ל-liveness.

**לוגים:** יוצאים ל-stdout. ב-OpenShift רואים אותם ב-`oc logs`, ובשרת Windows הם נכתבים ל-`logs\server.log`. כל שורה מתחילה ב-`[gantraah]`. שורות שכדאי להכיר:
- `listening on ...`: השרת עלה.
- `maintenance: space reclaimed`: התחזוקה הלילית רצה.
- `cleanup: ...`: הניקוי היומי מחק פריטים ישנים.

**גיבוי:**
- **PostgreSQL:** הגיבוי הרגיל של ה-DBA (`pg_dump`).
- **מסד מובנה:** `deploy/backup-embedded.ps1` עוצר את השירות לכמה שניות, אורז את התיקייה ומפעיל מחדש. ב-OpenShift עם PVC מגבים את ה-PVC (snapshot).
- **מומלץ:** לבדוק שחזור אחד על סביבת בדיקה בשבוע הראשון.

**עדכון גרסה:**
1. גיבוי.
2. מחליפים את האימג' (או את הקבצים `server`, `client` ו-`docs`). לא נוגעים ב-`.env`, ב-`data` ובלוגים.
3. מפעילים. המיגרציות רצות לבד.
4. בודקים את `/healthz` ומבצעים כניסה אחת.

**חזרה לגרסה קודמת:** תמיד יחד עם הגיבוי שנלקח לפני העדכון. מסד שעבר מיגרציה קדימה לא מובטח לעבוד עם קוד ישן.

**Reverse proxy:** חייב להעביר WebSocket בנתיב `/ws`, עם timeout ארוך. ב-Route של OpenShift זה כבר מוגדר (`haproxy.router.openshift.io/timeout: 1h`). בלי זה המערכת עובדת, אבל שינויים של אחרים מופיעים רק אחרי רענון, והפעמון וסימן "מי צופה" לא מתעדכנים.

**עצירה:** בסיגנל SIGTERM השרת מפסיק לקבל בקשות חדשות, מסיים את השינוי שבתהליך וסוגר את המסד בצורה מסודרת.

## 7. אבטחה

- **כניסה:** כל משתמש בוחר את המסגרת שלו בדף הכניסה, **בלי סיסמה**. רק הכניסה כהנהלת הענף מוגנת בסיסמה, שנשמרת כ-hash בטבלת `settings`. ברירת המחדל היא **ליורד**, וחובה להחליף אותה בהתקנה. זו החלטה מודעת של הלקוחה. חיבור ל-AD פתוח לדיון (סעיף 9).
- **עוגייה:** `gantraah_sid`, מסוג HttpOnly. עם HTTPS חובה להגדיר `COOKIE_SECURE=true`.
- **חשבון ישן:** בהפעלה הראשונה השרת יוצר חשבון בשם `admin`, מתקופה שבה הייתה כניסה עם שם משתמש. אם לא הוגדר `ADMIN_PASSWORD`, הסיסמה האקראית שלו נכתבת ל-`data/initial-admin.txt`. הממשק לא משתמש בחשבון הזה, אבל הנתיב `POST /api/login` עדיין קיים. **מוחקים את הקובץ אחרי ההתקנה**, ומומלץ להסיר את הנתיב בגרסה הבאה.
- **תעבורה יוצאת:** אין. המערכת לא פונה לשום כתובת חיצונית.
- **רכיבי צד שלישי:**
  - **בשרת:** `express` 5, `ws` 8, `pg` 8, `@electric-sql/pglite`.
  - **בממשק:** `react` 19 והגופן Rubik.
  - **ייבוא וייצוא Excel:** נכתבו בקוד שלנו, בלי ספריות.

## 8. סיכונים ונושאים פתוחים, לפי חשיבות

### 8.1 עבודה במקביל עם PostgreSQL חיצוני: **לטפל לפני הפעלה עם PostgreSQL**

**מה נבדק:** סימולציה של 4 משתמשים שעובדים על אותה משימה באותו רגע (שינויים, גרירות, יצירה ומחיקה של תלויות), בהיקף של 400 פעולות. הסימולציה רצה **על המסד המובנה** ועברה בלי אף שגיאה:
- אף תלות מעגלית לא נוצרה.
- כל המסכים הגיעו לאותו מצב.
- שינוי הגיע לשאר המשתמשים תוך 0.06 עד 0.12 שניות.

**למה זה עבד:** במסד המובנה כל הטרנזקציות עוברות בתור אחד, בתוך התהליך (`db.js`).

**למה עם PostgreSQL זה שונה:** עם `DATABASE_URL` אין תור כזה. הטרנזקציות רצות במקביל, ברמת הבידוד הרגילה (READ COMMITTED), וכל אחת מחשבת את התזמון על מצב שלא כולל את השינוי של השנייה. לפי הקוד, שלוש תקלות אפשריות:
1. **תלות מעגלית:** שני משתמשים מקשרים באותו רגע את אותן שתי משימות בכיוונים הפוכים, ושני הקישורים נשמרים. מאותו רגע כל שינוי הבא נדחה עם "השינוי יוצר תלות מעגלית", עד שמישהו מוחק אחת מהתלויות.
2. **שגיאת שרת:** אותה תלות נוצרת פעמיים באותו רגע, והמשתמש מקבל שגיאת מסד (UNIQUE) במקום הודעה מסודרת.
3. **ביטול שמוחק עבודה:** מונה הגרסה של התוכנית יכול לקבל אותו ערך בשתי טרנזקציות. אז "ביטול" של משתמש אחד יכול להחזיר צילום ישן ולמחוק שינוי של משתמש אחר.

**לא נבדק בפועל מול PostgreSQL**, כי לא היה כזה זמין בסביבת הפיתוח.

**התיקון המוצע** (קטן): נעילה אחת שעוטפת כל שינוי, בתחילת כל טרנזקציה ב-`db.js`:
```sql
SELECT pg_advisory_xact_lock(<מספר קבוע>);
```
כך כל השינויים עוברים בתור אחד, כמו במסד המובנה. הנעילה משתחררת לבד בסוף הטרנזקציה. בעומס של הענף (עשרות משתמשים) לא תהיה לזה השפעה מורגשת על המהירות. אחרי התיקון כדאי להריץ את אותה סימולציה מול PostgreSQL.

### 8.2 עותק אחד בלבד
- **מה מוחזק בזיכרון:** העדכונים החיים ורשימת "מי צופה באיזו משימה" מוחזקים בזיכרון של התהליך.
- **עם שני עותקים:** משתמשים שמחוברים לעותקים שונים לא יראו את השינויים זה של זה בזמן אמת.
- **עם מסד מובנה:** שני תהליכים בכלל לא יכולים לפתוח את אותה תיקייה. השרת שומר קובץ נעילה, ושרת שני ייעצר עם הודעה.
- **ב-OpenShift:** `replicas: 1`.

### 8.3 כניסה בלי סיסמה
כל מי שברשת יכול להיכנס בשם כל מסגרת. זו החלטה של הלקוחה, אבל זה הנושא הפתוח הראשון ברשימה שלה: חיבור ל-AD או סיסמה לכל מסגרת.

### 8.4 ביטול לפי מסגרת, לא לפי אדם
רשימת הביטולים שייכת למסגרת. שני אנשים שנכנסו בשם אותה מסגרת חולקים אותה, ואחד יכול לבטל פעולה של השני. זו התנהגות ידועה, לא באג.

### 8.5 דברים שלא נבדקו
- Docker Compose (`deploy/docker-compose.yml`).
- ייבוא מקובץ ה-Excel האמיתי של הענף. התכונה מסומנת כניסיונית.
- פתיחה של קובץ ההדגמה (`Ganttraah-demo.html`) בלחיצה כפולה מהדיסק.

### 8.6 מצב הקוד
- **מקור האמת:** הקוד המעודכן נמצא במחשב הפיתוח. במאגר ה-Git שלו יש עשרות שינויים שעוד לא נשמרו ב-commit, והמאגר ב-GitHub (`lironcohen11/Ganttraah`) לא מעודכן.
- **לפני המסירה:** לשמור הכול ב-commit, ולהעביר את הקוד עם ההיסטוריה בקובץ `git bundle` (סעיף 7 ב-`DEPLOY-INTERNAL.md`).
- **פיתוח בתוך הרשת:** אם יוחלט על זה, צריך npm mirror פנימי, או להעתיק את `node_modules` מבחוץ.

|---|---|
| **Backlog:** משימות בלי תאריך, מחוץ לגאנט. שיבוץ בגאנט, ושליחה חזרה ל-Backlog מכרטיס המשימה | טבלה חדשה `backlog`. נוצרת לבד |
| **מי צופה במשימה:** סימן עין בכרטיס, עם מספר ושמות המסגרות | הודעות חדשות ב-WebSocket (`view`, `presence`). דורש ש-`/ws` עובר |
| **אזהרה על שינוי:** כשמישהו אחר משנה משימה שפתוחה אצלך, והגנה על טקסט באמצע הקלדה | כל בקשה נושאת כותרת `x-client` עם מזהה הלשונית |
| **קריאת עדכונים אחד-אחד** בפעמון, וכפתור "סמן הכול כנקרא" | טבלה חדשה `notification_reads`. נוצרת לבד |
| **שם האחראי:** טקסט חופשי בכרטיס, לא חובה | עמודה קיימת (`tasks.owner`). לא נרשם בהיסטוריה |
| **ליטוש:** אנימציה לתפריטים, אפקט כשמסמנים "הושלמה", גרירת חלונות | אין |

אין מחיקה ואין שינוי של נתונים קיימים. העדכון הוא מהסוג הרגיל (סעיף 6).

## נספח: נקודות ה-API

כל הנתיבים מתחת ל-`/api`, וכולם (חוץ מכניסה) דורשים את העוגייה `gantraah_sid`.

| תחום | נתיבים |
|---|---|
| כניסה | `GET /units`, `POST /enter`, `GET /me`, `POST /logout`, `PUT /admin-password` |
| התוכנית | `GET /data` (כל מה שהממשק צריך, דחוס ב-gzip), `POST /undo`, `POST /redo` |
| פרויקטים | `POST /projects`, `PATCH`/`DELETE /projects/:id`, `POST /projects/:id/baseline` |
| משימות | `POST /tasks`, `PATCH`/`DELETE /tasks/:id`, `POST /tasks/:id/move`, `POST /tasks/:id/to-backlog` |
| Backlog | `POST /backlog`, `PATCH`/`DELETE /backlog/:id`, `POST /backlog/:id/schedule` |
| תלויות | `POST /dependencies`, `PATCH`/`DELETE /dependencies/:id` |
| ניתוח | `GET /tasks/:id/impact`, `POST /simulate`, `GET /delays` |
| היסטוריה | `GET /history`, `GET /history/meta`, `DELETE /history` (הנהלת ענף) |
| לוח עבודה | `GET`/`PUT /calendar`, `POST /calendar/special`, `DELETE /calendar/special/:id` |
| מבנה ארגוני | `POST /units`, `PATCH`/`DELETE /units/:id` |
| עדכונים | `GET /notifications`, `POST /notifications/:id/read`, `POST /notifications/read-all` |
| שונות | `POST /favorites`, `POST /import`, `PUT /settings/delay-reasons` |
| ישן, לא בשימוש בממשק | `POST /login`, `GET`/`POST /users`, `PATCH /users/:id` |

**WebSocket (`/ws`):**
- **מהשרת לדפדפן:** `changed` (התוכנית השתנתה: מי, מה, ומאיזו לשונית), `notify` (עדכון חדש בפעמון), `presence` (מי צופה באיזו משימה).
- **מהדפדפן לשרת:** `view` (איזו משימה פתוחה בלשונית הזו).
